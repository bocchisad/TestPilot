## Гипотеза и дизайн оценки

Проверяемая гипотеза: метки одно-строчных мутантов часто совпадают с покрытием изменённой строки, поэтому обучение на мутантах может почти копировать `cov_lines`. Исторические признаки co-change и недавних падений у синтетических строк часто пусты; это тоже проверяем на статистиках признаков, а не принимаем за факт без подсчёта. Отдельный реальный TEST — единственная основа вывода о превосходстве модели.

Каждый LORO fold удерживает целый репозиторий; внутри него TEST остаётся хронологическим. Отчёт считает `recall@10/20/30%` отдельно для synthetic и real. Для каждого разреза сравниваются модель и `cov_lines`, с числом коммитов и базовых коммитов, paired CI и покрытием временных значений. `partial=1` не входит ни в обучение, ни в метрики. Если реальные кейсы отсутствуют, метрика показывается как unavailable, не как ноль.

Предварительно зарегистрированные варианты обучения, все оцениваются только на реальных held-out TEST кейсах:

1. **Только мутанты.** Проверяет перенос синтетического правила на реальные дефекты.
2. **Только реальные примеры.** Показывает доступный сигнал реальных исправлений; если объём недостаточен, фиксируем `data_insufficient`.
3. **Смесь с весами источников.** Нормировать суммарный вес каждого источника, затем сравнить отношения synthetic:real `4:1`, `1:1`, `1:4`. Вес выбирать только на validation fold; TEST не использовать для настройки.

Отдельная диагностика на одинаковых real TEST кейсах сравнит:

- `cov_lines` как baseline;
- модель со всеми текущими признаками;
- ту же модель без `cov_lines`, сохранив остальные coverage features;
- модель только на признаках вне `cov_*`;
- ре-ранкер `cov_lines`, где модель на не-coverage признаках добавляет ограниченную поправку к baseline score, а сила поправки выбирается только на validation.

Метрики каждого варианта — real и synthetic раздельно; победитель для дефолта выбирается только по real. Доля тестов и экономия времени считаются для бюджета 10/20/30% по фактическим `dur` в миллисекундах; неизвестные `dur=-1` не подменять средним. «Запустить всё» — нулевая экономия времени и recall всех доступных падений.

## Критерий принятия

Критерий из запроса применяется к объединённым **реальным** held-out TEST кейсам:

1. real LORO macro recall@10% модели выше `cov_lines`;
2. paired 95% CI для объединённого real TEST Δ не включает ноль;
3. ни в одном репозитории real TEST Δ не ниже `−0.02`.

Критерий считается непроверенным и дефолт остаётся `cov_lines`, если real TEST не содержит примеров, CI нельзя вычислить или хотя бы по одному репозиторию нет оснований оценить Δ. Synthetic-only результат не открывает гейт и не меняет вывод.

## Этап 2 — сигнал сверх покрытия и real-only решение

### Гипотезы признаков

1. **Доля покрытых изменённых исполняемых строк** (`cov_lines / changed_executable_lines`): `cov_lines` уже есть и считает пересечение changed lines и coverage; доля отделит «больше строк из-за большего diff» от плотности связи теста с правкой.
2. **Расстояние в графе импортов** (`imp_dist` уже существует): ближе импортируемый модуль к тесту — больше шанс, что изменение дойдёт до теста, даже при нулевом line coverage. Проверить условный сигнал после `cov_lines`.
3. **Co-change тест↔файл** (`cc_max`, `cc_sum` уже существуют): совместные изменения в истории могут находить тесты, когда мутантные метки не меняют исторический граф.
4. **Недавние падения с затуханием** (новый признак поверх текущих `t_fail_rate/t_fail_cnt`): недавний flaky/unstable тест может быть диагностически важнее старой общей частоты.
5. **Тип правки** (новый категориальный/индикаторный признак: import, signature, body, test/fixture): разные виды изменений затрагивают разные классы тестов; текущие `ch_add/ch_rm/ch_nfunc` не кодируют семантический тип.

Для каждого указать доступность/долю sentinel отдельно на real и synthetic. Признаки с пустой историей у мутантов не трактовать как сигнал synthetic; сохранять их для реального обучения и проверить ablation без них.

### Реальные пары и сбор

**Основной источник real pairs 2A — PR-intermediate commits.** Для каждого PR с ≥2 коммитами `base` — merge-base PR head с `main`, а каждый коммит PR после base — `head`; дифф `base → head` — изменение для `select`. Positive test IDs должны существовать в base, присутствовать во всех четырёх прогонах, пройти в обоих повторах base и упасть в обоих повторах head. Test ID, отсутствовавший в base, не считается. Head SHA, встречающийся в нескольких PR, запускается один раз, а связанные PR объединяются для подсчёта. Единица счёта positive change — уникальный набор стабильных падающих test IDs внутри объединённой PR-группы; одинаковый набор на соседних промежуточных коммитах считается один раз. В каждой паре сохранять `test_modified_in_head`: менял ли этот head-коммит файл любого упавшего теста. Такой сигнал остаётся валидным для RTS, но отдельно показывается в отчёте. Порядок PR для выборки — newest-first.

**Revert-fix пары — только побочный отрицательный результат, не основной источник 2A.** Их историческое определение: `base` — fixed commit; `head` — тот же commit с откатом всех изменённых фиксом файлов пакета (`src/<pkg>/**` или legacy `<pkg>/**`, любого расширения), кроме test-like путей. `tests/`, `testsuite/`, `fixtures/`, `docs/`, `CHANGES*`/`CHANGELOG*`/`NEWS*` сохраняются. Откат исходников пакета должен применяться чисто; иначе `revert_conflict`. Такой дизайн позволяет regression test, добавленному в фиксе, напрямую наблюдать откат и смещает сигнал к `cov_lines`; дальнейшие revert-fix лиды не запускать. Принятый результат: revert-fix пары не дают сигнала вне regression-теста — 0/25 (click 0/13, Jinja 0/12); rule-of-three 95% upper bound ≈12%. Это отрицательный результат именно конструкции revert-fix, не PR-intermediate.

Исторический сканер обходит все локальные refs. Для merge-коммита набор изменённых путей и patch-id вычисляются по diff против first parent; внутренние коммиты merge также сканируются. Лиды с subject формата `Revert "…"` исключаются. Дедупликация стабильным Git patch-id схлопывает cherry-pick, merge-коммит и внутренний эквивалентный коммит в один lead с сохранением SHA/ref-представителей в аудите. Порядок лидов после дедупликации — newest-first отдельно по каждому репозиторию. Пакетные корни включают современные `src/<pkg>/` и legacy `click/`, `jinja2/` (включая `jinja2/testsuite/` как тесты), `attr/`/`attrs/`.

CI prefilter для feasibility получает заключения check-runs по каждому уникальному intermediate SHA. В PR, где у одного или более коммитов conclusion недоступен, fallback — только первый коммит этого PR; другие PR с полностью доступными статусами фильтруются: все `failure` плюс случайные 10% `success` с фиксированным seed. Общие SHA всё равно дедуплицировать. До pytest отдельно подготовить CI inventory: PR/commit counts, CI failure/success/unavailable counts, выборку и time forecast. Этот шаг не запускает pytest и завершается отчётом до отдельного OK.

Installation/build проверяются fail-fast до pytest. `env_incompatible` означает, что base или head нельзя установить/собрать на Python 3.13. Отсутствующие Git objects — отдельная причина `git_objects_missing`, не `revert_conflict` и не negative. Для пар предел 5 минут; для батча не более 30 минут включая инвентаризацию. Если общий лимит завершает пару раньше её индивидуального дедлайна, исход записывается как `batch_deadline`, отдельно от pair `timeout`; незапущенные тесты не становятся отрицательной меткой. После feasibility сохранить число PR с ≥2 коммитами, unique head SHA после dedup, CI-счётчики, unique positive changes, `test_modified_in_head`, среднее/медиану/p90 и артефакты. Полный 2A не запускать без отдельного OK.

Для исторического revert-fix контраста positive outcome требовал стабильного shared non-flaky test. В отчёте отдельно показано, падает ли что-то вне функции изменённого regression test; полученный ноль интерпретируется как отсутствие такого сигнала для этого дизайна, а не как оценка основного PR-intermediate источника.

В доступных артефактах week 6 такой истории нет; если локально больше логов не найдётся, использовать fallback из запроса: скрининг полной локальной истории коммитов по `fix|bug|regression|revert`, `fixes #`, `closes #` и записям в `CHANGES`. Кандидаты подтверждать по diff и тестам, не считать совпадение паттерна доказательством бага.

Для PR-intermediate pair `env_incompatible` означает, что base или intermediate head не удаётся установить/собрать на Python 3.13; обе установки проходят до pytest, иначе тесты не запускаются. Отсутствующие Git objects — отдельная причина `git_objects_missing`, не incompatibility и не negative. Каждая пара ограничена 5 минутами, включая окружения и четыре тестовых повтора; `timeout` — отдельный статус. Сохранять PR, base/head SHA, test IDs и исходы каждого повтора, changed paths, окружение, exit codes, wall time и причину включения/исключения. Для secondary revert-fix отдельно сохраняются исходные bug/fix SHA и статус `revert_conflict`.

Пилот revert-fix `c53d373` был проверкой процедуры, не PR-intermediate выборкой. Feasibility PR-intermediate ограничен первыми ~10 PR на репозиторий и ≤30 минут вместе с инвентаризацией. Фактические счётчики приведены в `docs/measurements/week7/real-pair-candidate-screening.md`. Полный сбор остановить до отдельного пользовательского OK. Outcome положительный только по описанному существующему-test правилу; перед включением в итоговый датасет PR-коммит и контекст бага проходят diff-аудит.

Пилот выполнен на click `c53d3732…` (head=`c74942a…`) под Python 3.13.18: 2136 shared test ID, base прошёл; head дал 9 стабильных новых падений, все — параметризованные варианты добавленных regression tests, других падений нет. Исключение обеих regression-test функций целиком убирает все 12 parametrized cases и даёт 0 positives. Каждая команда pytest исключила 31,000 Click stress tests через `addopts`. Окружение и сборка обеих версий совместимы. Это пример возможного смещения к `cov_lines`, не итоговая модельная метрика; полный лог — `docs/measurements/week7/real-pair-pilot.md`.

Для PR-intermediate 2A ключевой sample-size unit — unique positive change: уникальный набор failing test IDs внутри объединённой группы PR с общими head commits. Перед метриками требуется минимум **10 подтверждённых unique positive changes на репозиторий**; PR count и pair count не заменяют этот порог. Если изменений меньше 10, per-repo Δ получает `data_insufficient`, численное Δ не публикуется. Объединённые метрики показывать отдельно, если их расчёт валиден; критерий 2.4 нельзя считать выполненным при недостатке данных; default остаётся `cov_lines`. Synthetic события не увеличивают real sample size.

Доля падений вне добавленного regression test относится к secondary revert-fix результату: в click-пилоте она была 0/1, в калибровке — 0/25 (rule-of-three upper bound ≈12%).


### Сравнения и отчёт

Отчёт по real/synthetic × LORO/repository/fold включает `recall@10/20/30%`, `cov_lines` comparator, Δ/paired CI, `n_changes`, distinct base/change count, baseline score ties, positive counts, duration coverage. Для каждой source arm (mutant-only, real-only, weighted mixes) оценивать только на реальных held-out TEST; synthetic TEST показывать отдельной диагностикой. Признаки, варианты weights и выбор λ для re-ranker настраивать только на validation fold.

Success gate из раздела «Критерий принятия» применяется к real TEST. Если данных мало или CI включает ноль, вывод: «превосходство на реальных коммитах не доказано», default остаётся `cov_lines`. Это корректный исход.

Budget curve в `docs/measurements/week7/`: recall@10/20/30 и фактическая доля времени, сэкономленная моделью и `cov_lines`, плюс полный запуск как контроль. `partial=1` исключён; длительность с неизвестными значениями показывается отдельно.

## Этап 3 — `select --explain` (условно)

Только когда этапы 0–2 закрыты и осталось время. `select` добавляет к JSON top-3 feature contribution через LightGBM `pred_contrib`, версию schema увеличить ровно на 1, старые клиенты оставить совместимыми; человекочитаемый вывод использует те же contributions. Для `ranker=cov_lines` текст — «покрывает N изменённых строк». Score нигде не называть вероятностью.

## Подходы

- **Только ретроспективная диагностика W6:** быстрее, но real TEST в W6 пустой; не отвечает на вопрос пользователя.
- **Только увеличить synthetic N/добавить repo:** добавит mutant C, но не проверит перенос на реальные баги.
- **Порядок: 0.1 → пилот одной real pair (время и отчёт) → 0.2 → 0.3 → полный сбор real pairs (2A) → real-only оценка и абляции (2B) → при наличии времени Task 1 по synthetic N/четвёртому репозиторию → conditional explain.** Task 1 не запускается автоматически и не имеет предварительного разрешения на измерения; пользователь отдельно одобряет выбранные прогоны. Каждый шаг имеет свой коммит и CI, длинные прогоны требуют одобрения пользователя.

## Не цели и ограничения

- Не менять default с `cov_lines`, если не выполнен real-only критерий.
- Не представлять синтетические результаты как доказательство на реальных дефектах.
- Не смешивать `partial=1`, не делать подстановок для отсутствующей real метрики, не придумывать runtime.
- Не запускать долгие прогоны и не менять `main`.
- Не менять исходные незакоммиченные dry-run/env/fixture файлы в основной копии.
- У каждого этапа отдельный commit и PR в `feat/week7`, зелёный CI; в отчёте этапа — команды/вывод, пути артефактов, ограничения и невыполненное с причиной.

## Риски

- В week 6 только два real-positive коммита в click и ни одного в остальных наборах; real-only training/paired CI может остаться невозможным.
- Commit messages — лишь screening: 19 кандидатов не означают 19 подтверждённых реальных багов.
- Тест, добавленный фиксом, ретроспективен; переносить только тест/fixtures, фиксированный код не переносить.
- Нормализация выборки и тестов может протечь между train/val/test; группировать по bug/fix pair и исходному buggy change.
- W6 dry-run реконструкция in-sample, а attrs/new repo требуют новых независимых timing samples.
- Параметр роста N не гарантирует ≥10 distinct C именно в TEST.
